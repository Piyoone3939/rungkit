# 設計メモ

[English](design.en.md)

## 目標

SolidCraft（AIが操作できるOSSの3D-CAD）と同じ型を、ラダーで作る。

- 画面・CLI・MCP が同じコマンド処理を共有する
- AIは座標やクリックではなく、決まった結果になる命令で編集する
- AIが自分の結果を確かめられる（検証エラー、シミュレーション、形式検証）

## 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| ラングの表し方 | 直列・並列の木。座標は持たない | 実務のラダーはほぼこれで書け、三菱リスト形式と機械的に変換できる。配置は木から計算する |
| 直列・並列で書けない回路（ブリッジ回路） | 対応しない | 三菱リスト形式でも書けず、実務でもほぼ使われない。PLCopen XML 読み込み時は `E_NON_SERIES_PARALLEL` にする予定 |
| 最初のプロファイル | `melsec-iqr` と `iec` | 国内で多い三菱と、標準。FX5（X/Y が8進）は後から足せる |
| タイマー・カウンタの置き方 | 右端の出力（三菱流）だけ | IEC流の「ラングの途中に置くFB」は後から |
| AI向けの入出力 | `.ldt` テキストと JSON | ASCIIアートのラダーはAIが書けない（arXiv 2410.15200）。論理式なら書ける |
| 実装言語 | Go | 手元にあり使い慣れている。外部ライブラリはMCPの公式Go SDKだけ（プレゼンテーション層のみ）。画面はWebAssemblyで後から |
| 全体の構成 | オニオンアーキテクチャ | 下の「層」を参照 |

## 層

```
cmd/rungkit (組み立て)
  └ presentation: cli, mcpserver
      └ application: workspace, editing, scenario   ← インターフェースはここで宣言
          └ domain: ladder, profile, check, sim      ← 標準ライブラリだけ
  └ infrastructure: ldt, ldtest, jsoncodec, export/*, plcopen, filestore, locale  ← application のインターフェースを実装

共通: domain/i18n（メッセージの翻訳。どの層からも使う）
```

- ドメインは標準ライブラリ以外に依存しない。アプリケーションはドメインだけに依存する
- アプリケーションは、外の仕組みに頼るところを自分のインターフェースとして宣言する（`editing.Notation`、`workspace.Files` / `Notation` / `Exporter` / `ScenarioParser`）。Goの流儀どおり、使う側で宣言する
- インフラはそのインターフェースを実装する。プレゼンテーションはインフラを知らず、`cmd/rungkit` が両者をつなぐ
- `internal/architecture_test.go` が import を検査してこのルールを守らせる。テストコードは対象外（テストデータを作るのに `.ldt` のパーサを使ってよい）

## 編集コマンド

- すべての編集は「操作のリスト」として受け取り、プログラムの複製に順に適用する。全部成功し、触ったラングがすべて正しい形のときだけ置き換える（1つでも失敗したら何も変わらない）
- 途中の操作では形が崩れていてもよく、最後に検査する（複数の操作で組み替えられるように）
- デバイスの間違いなど `check` のエラーは断らずに返す。AIが続けて直せるようにするため
- 1回の適用が元に戻す1単位。元に戻したあとも、使ったIDは二度と配らない
- `insert_parallel` の範囲指定（target..to）は、2つの要素を含むいちばん内側の直列を探して、その中の範囲を並列で包む
- `.ldt` の表示では要素に `@e3` を付ける。この付いた文字列を貼り戻しても読める（IDは無視して新しく振る）

## 木の形のルール

- `Series` は最後の要素だけが出力側なら出力側、全部が条件なら条件側
- `Parallel` は全部条件なら条件側、全部出力なら出力側（出力の分岐）。混ざったら `E_MIXED_PARALLEL`
- ラング全体は出力側でなければならない（`E_NO_OUTPUT`）
- 正規化: 直列の中の直列・並列の中の並列は平らにし、要素1つの入れ物は外す

テキスト形式の文法はこのルールに反する木を作れない。JSONから来た木は `check` で弾く。

## ID

- 読み込み時に `r1, r2...`（ラング）と `e1, e2...`（要素）を振る
- 編集してもほかの要素のIDは変わらない。新しいIDは既存のIDと重ならない
- 要素のIDはファイルに保存しない（gitの差分を汚さないため）

## 三菱リスト形式への変換

- 条件側: 先頭は `LD`、直列は `AND`、並列は `OR`。複数要素のかたまり同士は `ANB` / `ORB`
- 出力の分岐: 最後以外の枝が条件を足すときだけ `MPS`、途中で `MRD`、最後に戻すとき `MPP`
- 条件なしの出力は `LD SM400`（常時ON）
- 同じ並びを2つの形で書く: `melsec`（1行1命令、読む・差分を見る用）と `gxw3`（GX Works3 の「編集 → ファイル読出」で取り込む CSV。GX Works3 自身の書き出しと同じ UTF-16 LE・BOM付き・タブ区切り・各項目を " で囲む・CR LF。1行目にプロジェクト名、2行目に機種、3行目に列の見出し、引数が2つ以上の命令は2つ目から次の行のデバイス列に書く。ラングのコメントは行間ステートメントになる。根拠は GX Works3 操作マニュアルの CSV 読出の節）

## STへの変換

- ラングを上から順に文にする。出力はその場で書く（ラダーと同じ）
- 出力の分岐は、共通の条件を一時変数 `_rN_k` に保存してから各枝で使う（MPSと同じ意味になる）
- 立上り・立下りは R_TRIG / F_TRIG、パルス命令（`MOVP` など）も R_TRIG
- 三菱のタイマー設定値は100ms単位として `T#...ms` に直す
- カウンタの `RST` はまだ書き出せない

## シミュレーター

- 時間は仮想時間。1スキャンの時間は固定（既定10ms、`.ldtest` の `scan` で変更）。実行するたびに同じ結果になる
- 命令はすべて毎スキャン実行する（評価を省略しない）。立上り接点・パルス命令は要素IDごとに前回の値を持つ
- 三菱のタイマー（`T`、低速タイマ100ms）は実機のしくみをまねる: 100msの時計はタイマーと関係なく進み、END処理（スキャンの終わり）でそのスキャン中に進んだ目盛りを数え、次のスキャンで `OUT T` を実行したときに、コイルがONなら（ONになった最初のスキャンでも）その分を現在値に足す（CPUユニット ユーザーズマニュアル 応用編「タイマの精度」）。入力が目盛りの途中でONになると、「設定時間＋1スキャン」より最大100ms早くONになる
- IECのタイマーは入力が入ったスキャンで計測を始め（経過0）、以後1スキャンごとに足す。出力は「設定時間＋1スキャン」後に見える
- 三菱のカウンタは設定値で止まる（設定値0は1として扱う）。IECの CTU は 32767 まで数える
- 実行時エラー（0で割る など）はスキャン番号・ラングID・要素IDを付けて返す
- `.ldtest` はテストごとに新しいシミュレーターで実行する。結果はJSONでも出せる（MCPの `run_scenario` がそのまま返す）

## MCPサーバー

- ツールは開く・作る・保存・表示・確認・編集・元に戻す・やり直す・書き出し・シナリオ実行の10個。編集は `edit_program` 1つに操作のリストを渡す形にし、ツール一覧を小さく保つ
- 保存するまでファイルは変わらない。保存先は `.ldt` / `.json` / `.xml` だけ（打ち間違いで別のファイルを上書きしないため）
- 文法と作業の流れは、接続時の instructions で伝える
- 読み書きできるのは作業フォルダ（`-root`、既定は起動したフォルダ）の中だけ。相対パスはその中で解決し、外を指すシンボリックリンクも断る。標準入力（`-`）は MCP の通信路なので断る。16MB を超えるファイルは読まない

## 2か国語対応

- メッセージは日本語の文をそのまま ID にし、英語の辞書（`domain/i18n/catalog_en.go`）を引く（gettext 方式）。既存のコードを大きく変えずに済む
- `internal/i18n_test.go` が、コード中の日本語の文字列すべてに英訳があること、書式（`%s` など）が日英で一致することを確かめる。英語で引数の順番を変えるときは `%[2]d` のように番号を付ける
- 言語は起動時に1回決める: `-lang` → `RUNGKIT_LANG` → `LC_ALL` / `LC_MESSAGES` / `LANG` → OS の設定（Windows のユーザーロケール）→ 英語
- パッケージの初期化時に作る値（エラーなど）は、表示するときに翻訳する（言語が決まる前に作られるため）
- 検証エラーの `code`（`E_READ_ONLY` など）は言語によらず同じ。AI や他のツールはコードで判断できる

## PLCopen XML

- 書き出し: ラングごとに左右の母線を置き、木から格子状に配置する（直列は右へ、並列は下へ）。接点・コイルは要素、比較・命令・タイマーはブロック、ブロックへの値は inVariable / outVariable でつなぐ
- 読み込み: 出力点（要素ID＋出力名）を単位に配線を union-find でまとめて「ネット」を作る。1つの入力に複数の線が来たら配線のOR、コイルと命令の ENO は入力のネットをそのまま通す
- 条件（接点・比較）はネットの間の辺、出力は「ネット → 終点」の辺にして、直列・並列への縮約で木に戻す。縮約しきれなければ `E_NON_SERIES_PARALLEL`。どの出力にもつながらない枝は捨てる
- 左の母線はすべてのラングで共通なので、母線を除いたつながりの単位でラングに分ける。ラングの順番と出力の実行順は位置（上から、左から）で決め、コメントは直後のラングに付ける
- タイマー・カウンタの Q から先につながる回路は、インスタンスを接点として読む別の枝に直す（タイマーが先に実行されるので同じ値になる）
- 三菱プロファイルは IEC の書き方に直して書き出し、`addData` にプロファイル名を残す。読み込みでこれを見つけたら、定数とタイマー設定値を三菱の書き方に戻す
- 公式スキーマ（Beremiz 同梱の tc6_xml_v201.xsd）で書き出しを検証した。テストではスキーマ検証はしていない（Go標準ライブラリにXSD検証がないため）
- Beremiz のビルドを通すために: すべての配線に経路の座標（`position`）を書く（スキーマでは省略できるが Beremiz は必須として扱う）、既定のタスク設定を書く、タイマー・カウンタの接点は `T0.Q` と書く
- Beremiz はコイルを位置順に、タイマーなどのブロックをその後に実行する。`executionOrderId` はブロックにしか効かないので、ラング順どおりにはできない（[eval/interop](../eval/interop/README.md)）

## ラダー図の表示とブラウザ版

- `render` はラングの木から格子の配置を計算し（直列は右へ、並列は下へ、出力は右の母線に寄せる）、同じ配置を文字（`ascii`）と SVG（`svg`）で描く。SVG の要素には `data-elem`（要素ID）と、デバイスコメント入りの `<title>` を付ける。色は `currentColor` なので、ページのライト・ダークに従う
- ブラウザ版は Go を WebAssembly にしたもの（`cmd/rungkit-web`）。ファイルシステムがないので `filestore.Memory` を使い、ワークスペースはそのまま使う。`internal/presentation/web` が JavaScript から呼べる関数（update・export・format・runScenario など、JSON を返す）を用意し、画面（`web/`）はそれを呼ぶだけ
- 入力は端末の localStorage に保存するだけで、どこにも送らない。図の要素をクリックすると、`.ldt` のその要素の行に移動する
- 画面は CAD 風の作業台（青灰色の地・細い線で区切った平らなパネル・方眼の作業面・タブ付きのリボン・ステータスバー）。左は「テキスト」と「構成」（ラングとデバイスの木）、図の下に拡大・縮小、下にシナリオのドック。明るいテーマにも切り替えられる。色は `web/style.css` の変数にまとめる
- アイコンは rungkit のために描いたもの（`web/index.html` の SVG）。ラダー記号をもとに、金属の接点板・青いコイル、追加は緑・削除は赤のバッジ。グラデーションは共通の定義を使う
- 部品パレットの部品（a接点・b接点・立上り・立下り・比較・OUT・SET・RST・タイマー・カウンタ）を要素の上へドラッグすると、置いた位置で前・後・並列（下側）・置き換え（中央）が決まる。要素以外に置くと新しいラングになる。部品をクリックすると、選択中の要素の後ろ（出力なら並列）に置く
- 図の上でも編集できる。要素かラングをクリックして選び、ボタン（前に条件・後に条件・並列に追加・置き換え・デバイス変更・削除・ラング追加・ラング削除）で操作する。中身は MCP と同じ編集コマンド（`rungkit.edit`）で、結果はテキストに書き戻す。テキストが唯一の元データなので、図の編集で `//` のコメントは消える（初回に確認を出す）。元に戻すはページ側でテキストの履歴を持つ
